## 3. Gaps, drift, and contradictions

These findings retain the earlier code review and reconcile it with `docs/CornerBrief-PRD.txt`. Differences from the PRD are identified by page; build-prompt-only implementation choices are distinguished from PRD requirements. Source authenticity, legal authority and human approval are not independently verified.

1. **Rule sourcing has advanced beyond the starter instructions.** The PRD starter table lists H-1011 slopes/landing and ADA curb-ramp limits as needing sources, and the flare entry as needing current H-1011 (`docs/CornerBrief-PRD.txt`, p. 7); `BUILD_PROMPT.md` uses `needs_source`. Current H-1011 files include separate `*-ACCEPT` and `*-DESIGN` rules plus general notes, with `status: verified` and `reviewed_by: null` (for example `rules/nyc/H1011-T1-RAMP-RUNNING-ACCEPT.yaml`, `rules/nyc/H1011-T1-RAMP-RUNNING-DESIGN.yaml`, `rules/nyc/H1011-N27-28-CASE-SELECTION.yaml`). The supplied drawing is `docs/sources/H-1011-1.pdf`. `README.md` explicitly limits sourcing to sheet 1 and says sheets 2–9 were not reviewed. ADA rule files have also advanced to verified with third-party source citations (`rules/federal/ADA-2010-405-2-SLOPE.yaml`); the two NYS stubs still need sources (`rules/nys/`). This is documented source-status drift from the PRD, not a reason to revert sourced files to empty stubs. H-1011 remains partial coverage, not a fully validated design standard. This review did not independently authenticate the PDF or every transcribed quote/limit.

2. **“Verified” does not mean engineer-reviewed.** `README.md` says Claude checked sources and no person reviewed them. ADA YAML identifies a third-party Corada reproduction and requests confirmation on ada.gov (`rules/federal/ADA-2010-405-2-SLOPE.yaml`). `cornerbrief/rules.py::validate_rule` checks required metadata, but does not verify that a stored limit is supported by its quote or that a source is current. All six precedence files also have `reviewed_by: null` (`rules/precedence/*.yaml`), and `load_precedence` does not require reviewer metadata. `cornerbrief/orchestrator.py::rule_review` counts rule review gaps, not precedence review gaps. The PRD explicitly requires a person to review each rule, reviewed precedence, and a civil engineer to review the rules and three briefs before the final demo (`docs/CornerBrief-PRD.txt`, pp. 5–6, 12). Treat legal/source correctness and that human acceptance condition as unverified.

3. **Two distinct status vocabularies must remain distinct.** Rule lifecycle statuses are `verified`, `needs_source`, and `superseded` (`cornerbrief/rules.py`); numeric outcomes are `limit exceeded`, `no conflict found`, `unknown`, and `not applicable` (`cornerbrief/models.py`). Corner summaries are `probably standard`, `probably custom`, and `unknown`; internal Skeptic verdicts are `pass` and `rework` (`cornerbrief/models.py`). Neither a `verified` source nor an internal Skeptic `pass` is a compliance outcome. The four numeric outcomes match PRD p. 5; the scope table says standard/custom/unknown (p. 1), while constrained acceptance explicitly says probably custom (p. 12). Thus the tentative headline vocabulary is consistent with the PRD intent, although its evidentiary basis is weak (finding 6). The extra stale label extends R2’s measured/assumed/missing vocabulary to implement R20 (`docs/CornerBrief-PRD.txt`, pp. 8–9).

4. **Stage distinctions are an implementation extension.** `cornerbrief/rules.py` additionally requires `stage` with general/design/work-acceptance values, beyond the build prompt's listed metadata. `cornerbrief/checker.py` separates work acceptance from design targets, and UI/export label the latter “If this corner is rebuilt” (`cornerbrief/static/app.js`, `cornerbrief/review_export.py`). Existing-ramp readings should not be presented as proposed design checks. The PRD starter table distinguishes a design margin but does not define the implementation’s stage field or separate ACCEPT/DESIGN IDs (`docs/CornerBrief-PRD.txt`, p. 7). Reconcile the table to the current staged rules rather than merging targets with acceptance checks.

5. **Framework and rendering stack differ from the build prompt, not a prescribed PRD framework.** The PRD requires a simple browser 3D model (p. 2, R11 p. 8) but names neither FastAPI nor three.js. `BUILD_PROMPT.md` names FastAPI and three.js; `requirements.txt` and `cornerbrief/app.py` use Starlette, and `cornerbrief/static/app.js::drawModel` projects geometry onto a 2D canvas. `README.md` discloses the substitution. The renderer caps pixel ratio at 1.5 and redraws on interaction/resize, but this is not evidence of three.js or target-device performance testing (`cornerbrief/static/app.js`).

6. **“Probably standard” is not derived from successful rule checks.** `cornerbrief/orchestrator.py::decide_status` accepts `outcomes` but never uses it: after data sufficiency, only program complexity and recorded obstacles determine standard/custom. Missing sidewalk width, legal grade, and existing ramp type remain site questions (`cornerbrief/evidence.py`, `cornerbrief/site_visit.py`). The standard replay suggests C1 even though path width is absent (`data/replay/standard/site_analyst_0.json`, `rules/nyc/H1011-N27-28-CASE-SELECTION.yaml`). Inference: the headline can sound more authoritative than the evidence permits, especially because it also controls whether planning runs. This qualifies R4/R25 and the PRD requirement not to hide uncertainty (`docs/CornerBrief-PRD.txt`, pp. 1, 8–9).

7. **Option checking is survey checking, not proposed design validation.** `RampOption` has a case name, rationale, and evidence keys, but no proposed dimensions (`cornerbrief/models.py`). `analyze` calls `run_checks` on the same surveyed evidence regardless of option, while `checked_ramps` checks labels and units rather than numeric rule outcomes (`cornerbrief/orchestrator.py`, `cornerbrief/parts_kit.py`). Consequently planning can be generated for an obstacle-free, sufficient corner even if some limits are exceeded. The build prompt’s “checks each option” language overstates this implementation (`BUILD_PROMPT.md`). The PRD’s flow text says a failed rule check or weak claim returns to the analyst (p. 3); code instead retries only when the Skeptic requests rework or analyst validation fails, so a numeric exceedance alone does not trigger rework (`cornerbrief/orchestrator.py`).

8. **Freshness and join failures are warnings with gaps.** `is_stale` only compares parseable survey and later construction dates. An absent/unparseable survey date can still leave a numeric value labeled measured; old measurements without a later construction record remain current under this logic. `latest_construction` uses all supplied progress rows without filtering matching IDs, while `join_report` warns separately and `data_sufficient` ignores join notes. This can misclassify freshness or allow an unmatched/missing progress record through the gate (`cornerbrief/evidence.py`). Dataset-wide age is not checked there. This limits the R2/R20 provenance and staleness promise and the outdated-measurement risk response (`docs/CornerBrief-PRD.txt`, pp. 8–9, 13).

9. **Road ownership is not conservatively resolved when unconfirmed.** Only `road_control == "state"` forces unknown in `cornerbrief/applicability.py`. `road_control == "not_recorded"` creates an assumed city-street evidence item and a site action while normal applicability continues (`cornerbrief/evidence.py`, `cornerbrief/site_visit.py`). The explicit-state test does not cover this distinction (`tests/test_core.py::test_state_road_returns_unknown`). The PRD says unknown until ownership is confirmed and that the tool should not assume (`docs/CornerBrief-PRD.txt`, p. 6); the unrecorded-ownership branch falls short of that caution. A person must decide whether that assumption is acceptable even for a clearly synthetic demo.

10. **Missing/stale path skips numerical evaluation, not the checker function.** `BUILD_PROMPT.md` says to skip limit checks. `analyze` calls `run_checks(..., [])` to generate unknown/not-applicable rows, with no dimensions to numerically evaluate, and still computes conflict metadata. `tests/test_flow.py::test_missing_or_stale_corner_refuses_design` tests result categories, not that the checker is never invoked. The PRD requires refusal to propose a design and a site list, not zero checker-function invocations (R3 p. 8; acceptance p. 12). This is a build-prompt wording/trace distinction, not evidence that missing measurements are numerically checked (`cornerbrief/orchestrator.py`, `cornerbrief/checker.py`).

11. **Agent guardrails are narrower than the README claim.** `README.md` says checks reject unsupported numbers and compliance claims. `check_text` recognizes specific words and whether a numeric token appears anywhere in the payload, not whether that number supports a specific statement (`cornerbrief/guards.py`). Records summary is not text-checked before entering the writer payload, and Skeptic challenge text is displayed without this guard (`cornerbrief/orchestrator.py`, `cornerbrief/static/app.js`, `cornerbrief/review_export.py`). An invalid Skeptic schema sets `verdict = "pass"` and allows subsequent processing. These are gaps despite useful schema/claim tests (`tests/test_flow.py`), affecting R6 and the PRD’s every-run prohibition on compliant/safe claims (`docs/CornerBrief-PRD.txt`, pp. 8, 12).

12. **The visual is not the single modeled takeoff described in the PRD and build prompt.** The PRD requires one measured takeoff, counts, and all planning results updating together (`docs/CornerBrief-PRD.txt`, pp. 3, 9, 12). `cornerbrief/takeoff.py` emits area, volume and length items but no count item (R21). `cornerbrief/planning.py` calls `build_scene(ramps)` separately from `build_takeoff(build_parts(ramps))`. In `cornerbrief/model_3d.py`, two drawn curb pieces are each two feet long and ramp rise is capped at a fixed curb height; `cornerbrief/parts_kit.py` counts curb length as ramp width plus the assumed extra length. The renderer also exaggerates vertical coordinates (`cornerbrief/static/app.js`). These are concept illustrations, but model/quantity fidelity and “every result updates” need more than the existing scene-inequality assertion (`tests/test_flow.py::test_one_dimension_change_updates_every_planning_result`).

13. **Rate handling and labels are incomplete across outputs.** `cornerbrief/cost.py` returns unknown for missing cost rates and flags old cost rates. `cornerbrief/crew_sequence.py` instead accumulates available hours and lists `unknown_rates`, with no rate-age flag. UI renders hours with a sample-rate label but does not render missing crew rates; Markdown prints labor hours without their own sample/missing/age disclosure (`cornerbrief/static/app.js`, `cornerbrief/review_export.py`). 14. **Export drops useful provenance.** The browser evidence table shows dates; the exported evidence table omits `EvidenceItem.date`. The export gives aggregate cost/sample information but no individual rate/source/date table, and safety questions lose the URL links shown in the browser (`cornerbrief/static/app.js`, `cornerbrief/review_export.py`, `cornerbrief/models.py`, `cornerbrief/cost.py`, `cornerbrief/safety_questions.py`). A downloadable brief should carry the same caution and traceability as its on-screen context (R2/R7, `docs/CornerBrief-PRD.txt`, p. 8).

15. **Rule review aging is flagged, not enforced.** The PRD risk response calls for expiring rules that need review (`docs/CornerBrief-PRD.txt`, p. 13). `cornerbrief/orchestrator.py::rule_review` reports source checks over a year old, but `cornerbrief/checker.py` continues to use verified rules regardless of age or null reviewer. A source-check warning is not an expiration policy; the engineer must agree on one.

16. **Real-corner scope and email integration have changed.** The original PRD asks for three real corners (pp. 1–2), while `README.md` and `data/corners/*.json` provide synthetic examples. The requester explicitly defers real-data fetch, so this is an accepted scope adjustment for this review, not a demo failure. The PRD also suggests a service API key in an environment variable (p. 11); `cornerbrief/email_delivery.py` implements SMTP credentials instead. Guarding is implemented, but service/domain selection and live delivery remain open under R12 and the PRD p. 14 question.
